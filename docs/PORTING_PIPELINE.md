# Porting pipeline and milestones

## Pipeline
1. **Intake:** identify title, engine, source availability, target PSP model and rights.
2. **Inventory:** list files, sizes, extensions, likely executable and asset formats.
3. **Feasibility gate:** classify as source port, engine reimplementation, asset-only
   conversion, or infeasible without major reverse engineering.
4. **Profile:** define renderer, input, audio, filesystem, threading, memory and asset adapters.
5. **Port:** compile engine code for Allegrex/MIPS; replace unsupported APIs.
6. **Optimise:** reduce draw calls, texture sizes, streaming pressure, effects and CPU work.
7. **Package:** build EBOOT.PBP with PSPSDK tools.
8. **Validate:** boot, controls, save/load, audio, scene transitions, long-run stability.
9. **Report:** record FPS, memory headroom, crashes, missing assets and known limitations.

## Milestones
- M0 (1–2 days): toolchain setup; build and run smoke-test app in PPSSPP.
- M1 (2–5 days): Python analyser, JSON report, deterministic output and tests.
- M2 (1–2 weeks): asset inspection/conversion plugins for one open format.
- M3 (2–6 weeks): port a small open-source PC game with available source.
- M4 (game-dependent, weeks to months): one engine-specific PC port profile.
- M5 (research project, months+): investigate a single PS2 title's assets and engine.
  PS2 support is per-title/per-engine, not generic ISO conversion.

## Feasibility categories
- A: source code builds with PSP toolchain after modest changes.
- B: source exists but renderer/audio/input/memory need significant adaptation.
- C: source unavailable; substantial reverse engineering required.
- D: arbitrary binary/ISO conversion requested; not a viable direct pipeline.

## Acceptance checks
- Clean build from a fresh checkout.
- EBOOT.PBP is generated by PSPSDK, not renamed from another executable.
- Runs in PPSSPP, then on hardware.
- No proprietary assets committed to the repository.
- Each supported title has explicit compatibility and performance results.
